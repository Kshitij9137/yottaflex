## 8. Limits of this validation

- **Perfect detector scores are expected, not impressive.** The anomalies are deterministic signatures, so a rule that matches the signature finds them all. What the result does show: the ground truth is correct, the injection touched only labelled records, no decoy is flagged, and the clean baseline passes every rule. A real system would see fuzzier anomalies and trade precision against recall.
- **Shared helpers.** The validator reuses `dates.months_between` and `labels.derive_label` from the generator, so a bug inside those two functions would not be caught here. Every other derived value is recomputed with independent code.
- **No natural key for Employee.** The table carries no personal attributes by design, so duplicate detection relies on primary-key uniqueness (`DUP-ROW` is not applied to it).
- **Leak detection is timestamp-based.** It catches rows recorded after their own snapshot day and rows dated after exit. A leak with a falsified `recorded_at` would need lineage checks outside this dataset.
- **Bounds-based salary check.** Merit is not stored as its own event, so salary steps are validated against allowed ranges, not exact amounts.
